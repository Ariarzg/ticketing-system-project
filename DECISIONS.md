# Design Decisions

> 🇮🇷 **A Persian (فارسی) version of this document is available in a separate file: [DECISIONS.fa.md](DECISIONS.fa.md).**

Running log of decisions made while planning. Each one should be demonstrable in the README.

## Product / lifecycle
| # | Decision | Why |
|---|---|---|
| D1 | Statuses: Open, In Progress, Answered, Closed. Any agent reply -> Answered. Client reply -> In Progress. Agent status change without reply (Open) -> In Progress. | Brief's lifecycle was ambiguous; "In Progress" = ball is with the agent, "Answered" = waiting on client. |
| D2 | **Only staff can close a ticket**: the assigned agent or the supervisor. Clients cannot. Closed is final: no reopen, no replies. | Owner's call; keeps the transition table small. |
| D3 | Transitions live in one function `(status, event, role) -> newStatus or error`, used by every endpoint. | Single source of truth for the lifecycle; easy to unit test. |
| D4 | "Needs attention" is derived from status (Open, In Progress), no extra column. Highlighted in list + quick filter with count. The UI labels it «نیازمند پاسخ» ("needs a reply"), the same words the row's screen-reader text uses. | No extra state to keep in sync. |

## Users / auth
| # | Decision | Why |
|---|---|---|
| D5 | Signup fields: name, email, password, organization (D24). Signup always creates a Client; role never comes from the request. The seed creates the supervisor; agents are clients the supervisor promotes (D23). | Prevents privilege escalation. |
| D6 | Email + password login, JWT in an httpOnly cookie, short-lived. Server loads the user on each request. | Simple, secure enough; deleted/changed accounts take effect at once. |
| D7 | The organization is chosen at signup from a list the supervisor manages (D24) and copied onto the ticket at creation. Staff can filter by organization (the supervisor over all tickets, an agent over their assigned ones, D25). | Brief mentions a department filter but defines no field. Until v1.2 this was one of three fixed departments; organizations replaced them. |
| D8 | Slug = slugified name + UUID. | Unique, no collision handling. |

## Architecture
| # | Decision | Why |
|---|---|---|
| D9 | **Polling (every 3-5 s) for ticket threads, not WebSockets.** State this at the top of the README. | Brief never asks for real-time. WebSockets only if everything else is done. |
| D10 | Middleware layers: `authenticate` -> `requireStaff` (agent or supervisor) or `requireSupervisor` -> the ticket scope enforced in the query by one function, `ticketScope`: a client's own tickets (`user_id = me`), an agent's assigned tickets (`assignee_id = me`, D25), or all for the supervisor. | Server is the real guard; client route guards are UX only. |
| D11 | Foreign ticket returns 404 from the API; UI shows "Not Authorized" toast and redirects to `/tickets`. | Doesn't reveal that an ID exists. |
| D12 | Stack: Next.js 16 monolith (Route Handlers for the API), Bun runtime (`bun run --bun next ...`, `bunVersion` in `vercel.json`), HeroUI v3 + Tailwind v4, TanStack Query, zod, jose, `Bun.password`. Zustand only if a real need appears. | Owner's choice; one deployable app, fewest moving parts. |
| D13 | Database: Neon Postgres + Drizzle ORM. Two Neon branches: `production` and `dev`, each with its own connection strings in env vars. App uses the pooled URL; migrations use the direct URL. | Hostable demo; dev and prod data never mix. |
| D14 | The Next.js 16 `proxy.ts` (renamed from `middleware.ts`) only does the coarse check (no valid cookie -> redirect to `/login`). Role and ownership checks (D10) live in route handlers / data functions. | Proxy is a redirect layer, not the security boundary. |
| D15 | UI is Persian, RTL (`lang="fa" dir="rtl"`), Vazirmatn font, Jalali dates via `Intl` (`fa-IR-u-ca-persian`), Tailwind logical classes (`ms-`/`me-`/`text-start`), `dir="auto"` on user-written text, all UI strings in one file. React Aria (under HeroUI) is wrapped in `I18nProvider locale="fa-IR"`. User text shown in one line gets `dir="auto"` plus `text-right`; an empty input stays `dir="rtl"` and switches to `auto` once something is typed. | Brief is Persian; mixed Persian/English user text must render correctly. Without the provider React Aria follows the browser language, so an English browser got left-to-right toasts and dropdowns and reversed arrow keys. `dir="auto"` alone moved English titles to the left and made an empty Persian placeholder left-to-right. |
| D16 | Deployed demo on Vercel. | Owner's choice. |
| D17 | A `message` is one reply in a ticket's thread (author, body, timestamp). The ticket's `description` is shown as the first bubble. Messages drive status transitions (D1). | Keeps the thread simple. |
| D18 | Visual language: a calm product UI built only from HeroUI tokens in `globals.css`: one mint accent (`oklch(82% 0.12 155)`, from the HeroUI theme builder) with green-grey neutrals, one radius rule (cards and fields 12-16 px, buttons and chips are pills), Phosphor icons only (one family, regular weight, filled for the active nav item). The mint is for fills (primary buttons, logo, your own message bubbles); text in the accent colour uses a darker green (`--accent-soft-foreground`, `oklch(49% 0.1 155)` in light mode), so all text meets WCAG AA (4.5:1) and focus rings 3:1 in both themes. Colour belongs to status ("open" is a solid mint chip); priority is shown by a signal icon and only "high" is red. Motion is limited to a short fade-and-rise on page content and list rows, and is switched off for "reduce motion". | A support desk is used all day: quiet, consistent, no colour outside the tokens. The mint replaced the first cobalt accent on 2026-10-17; the builder's light values failed contrast wherever the mint was used as text (down to 1.5:1), so those tokens were darkened. |
| D19 | Light and dark themes. The default follows the operating system; a toggle saves the choice in `localStorage`. An inline script in `<head>` sets `class="dark"` on `<html>` before the first paint (no flash). Components use token utilities (`bg-surface`, `text-muted`, `border-border`), never fixed colours. | Dark mode works from day one instead of being bolted on. |
| D20 | App layout: sidebar on the start side (the right) on desktop, a top bar with a drawer on phones. Tickets are list rows, not tables (they reflow on phones). The ticket page is the thread plus a facts panel; on phones the panel comes first for agents (status buttons) and after the thread for clients, who get the status chips under the title. Filters are status tabs with counts (a select on phones, where six tabs do not fit) plus a search/priority/organization toolbar (priority for staff only, D26); "needs attention" is a tab for staff, and the supervisor also gets "agents needed" (D25). The counts follow the search, priority and organization, so "all" matches the list. | Standard pattern for tools like this; every screen works at 375 px. |
| D21 | The seed creates exactly one organization, the default «آفتاب آسا جنوب» (D24), and one account in it: the supervisor `supervisor@ticketing.com` (until v1.1 it was the agent `agent@ticketing.com`). No demo clients, tickets or messages. Clients (including the recruiter) sign up themselves. The seed finds the default organization by its `is_default` flag, inserts only what is missing and never deletes, so it is safe to run again, also on `production`. | The live database holds only data that real use created, with no fake records mixed in. A supervisor must still be seeded because signup can never create staff (D5); agents come from promotion (D23). |
| D22 | Vercel functions run in Frankfurt (`"regions": ["fra1"]` in `web/vercel.json`), the same region as the Neon project (aws-eu-central-1). | Every API request makes several database queries; keeping functions next to the database avoids a transatlantic round trip on each one. |

## Roles and organizations (v1.1, v1.2)
| # | Decision | Why |
|---|---|---|
| D23 | A third role, **supervisor**: it changes status and closes like an agent (until v1.3 it also replied; since v1.3 it does not, D25), plus a supervisor-only list of agents (`/agents`) and promoting a client to agent from the client's profile (`POST /api/users/{slug}/promote`). Only a client who has filed no tickets can be promoted (409 `has_tickets`, or `not_a_client` for staff); there is no demotion yet. Every agent-only check became one helper, `isStaff(role)` (agent or supervisor); only the agents list and promotion ask for the supervisor by name (`requireSupervisor`). | Owner's request. One helper instead of copied checks keeps the two staff roles from drifting apart. Staff never own tickets: a staff profile shows no ticket list, and a staff member's replies on their own tickets would count as agent replies. |
| D24 | Organizations replace the three fixed departments: an `organizations` table and `organization_id` on users and tickets (copied onto the ticket, D7). One organization is the default (`is_default`, kept unique by a partial unique index): the seed creates it, it cannot be deleted, and all staff belong to it: the supervisor is seeded into it, and promoting a client to agent moves them into it (v1.2.5; migration `0005` moved staff who were elsewhere). The supervisor lists, adds, renames and deletes organizations at `/organizations`; deleting one moves its users and tickets to the default in one transaction. `GET /api/organizations` is public and returns names only, because signup needs it. The browser looks names up by id from that one cached list instead of joining in every query. Organizations do not decide who sees a ticket; assignment does (D25). | Owner's request. Staff serve every organization, so they sit in the default one instead of a client's. A flag, not the name, marks the default, so renaming it is safe. Foreign keys without cascade make the database refuse to delete an organization that still has people or tickets, as a guard behind the route. |

## Assignment and priority (v1.3)
| # | Decision | Why |
|---|---|---|
| D25 | A new ticket is seen only by its client and the supervisor. The supervisor assigns it to one agent (`POST /api/tickets/{id}/assign`, `tickets.assignee_id`), **once**: no reassigning. An agent sees only the tickets assigned to them, and on `/users` only the clients of those tickets; any other ticket or profile is 404 for them (D11). The supervisor keeps the status buttons but no longer replies (the lifecycle refuses with 403). The supervisor's `/tickets` has an "agents needed" view: unassigned tickets that are not closed. The status route now applies the same ticket scope, so an agent cannot change a ticket that is not theirs. | Owner's request: the supervisor decides who works on what. Assigning once keeps one agent accountable for a ticket. "Not closed" because the supervisor may close spam or duplicates without assigning them. |
| D26 | The priority is set only by the supervisor, together with the agent, when assigning. A new ticket has no priority (`null`, shown as «هنوز تعیین نشده»); migration `0006` cleared the priority of existing unassigned tickets. Clients never see the priority or who their agent is: the API blanks both for them (`forViewer`), not only the screen, and ignores a client's priority filter. | Owner's request. A client-chosen priority was not trustworthy; the supervisor sees all tickets and can compare them. Hiding a field only on screen would still send it to the browser. |

## Routes
`/login`, `/signup`, `/tickets`, `/tickets/new`, `/tickets/{id}`, `/users` (staff), `/users/{slug}`, `/agents` and `/organizations` (supervisor only).
- `/tickets`: client sees own tickets (timestamps, status). The supervisor sees all, an agent their assigned ones (D25); default sort `updated_at` desc, filters: status, priority (staff only), organization; one search box over title + author name; pagination. The supervisor also has the "agents needed" view.
- `/tickets/{id}`: thread + composer for the client and the assigned agent (disabled when Closed); the supervisor gets a notice instead. Staff additionally get the priority, the agent and the status control; the supervisor gets the assign panel while the ticket is unassigned.
- `/users`: staff only, clients with organization and open-ticket count (every status except Closed), name search; an agent sees only the clients of their tickets. Clients get a "Not Authorized" toast.
- `/users/{slug}`: owner, the supervisor, or an agent for the clients of their tickets. Summary + tickets (an agent sees only theirs). On a client's profile the supervisor gets the "promote to agent" button.
- `/agents`: supervisor only, every agent with organization, name search.
- `/organizations`, `/organizations/new`, `/organizations/{id}`: supervisor only; list, add, rename, delete (D24).
- Also: logout, `/` redirects to `/tickets`, 404 page, redirect to `/login` on expired token, links hidden from roles that cannot use them.
